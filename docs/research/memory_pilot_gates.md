# メモリ導入前の判定実験（G0〜G3）

[memory_pilot.md](memory_pilot.md) の方針を、メモリ実装の前に小さな実験で判定するための作業指示。
目的は方針決定であり、論文用の評価ではない。結論は各ゲートの「判定」に従って書く。

## 前提

- リポジトリルート: `/work`。実行ルート: `/work/skill_moe/skillnet`。環境: `cd /work && source env/activate.sh`。
- 既存の未コミット変更を reset・上書きしない。Docker関連ファイルは作らない。
- 公開 SkillNet-LIBERO-40（`pi05_libero_moe_skill_4_40`、重みは `.skillnet-state/checkpoints/`）を固定して使う。学習はしない。
- 新規コードは `skill_moe/skillnet/examples/memory_pilot/` に置く。既存モジュールは、記録用のフック追加など最小限の変更にとどめる。
  メモリ・フックが無効のときは、元の推論と同じ出力になること。
- 出力は `/work/.skillnet-state/outputs/memory-pilot/<gate>-<実行ID>/` に保存し、既存の結果を上書きしない。
- GPU: H200 ×1（143GB）を複数の作業で共有する。`env/activate.sh` が `XLA_PYTHON_CLIENT_PREALLOCATE=false` を設定するので、これを外さない。
  PyTorchの評価も含め、1プロセスで占有しない。作業は並行して進むため、他の担当のディレクトリ・ファイルを編集しない。

## 背景（コードで確認済み）

`src/openpi/models/gemma_moe_skill.py` の `MoEFeedForward` では、skill_embeds（skill IDの埋め込み64次元＋位置埋め込み、mask付きの複数トークン）を
cross-attention した出力が、`router_logits` だけに使われる。action expert は `gemma_300m_moe_4` で、4エキスパートのtop-1と共有エキスパート1つ。
したがって、skill経路で変えられるのはエキスパートの選択とゲート値だけ。
この経路が行動をどれだけ左右するかが、メモリの注入点を決める最初の分岐になる。

## 段階1: 記録機構（G0・G1・G2の共通基盤）

既存の評価経路（`examples/libero/main_skill_obj_test_moe_skill.py` とポリシー側）を使い、ロールアウトから次を記録する。

- タスク名・suite、初期状態ID、エピソードID、ステップ番号、成功／失敗
- 方策への入力そのもの: 画像（縮小可）、ロボット状態、プロンプト、skills・skill_mask（推論に渡した値）
- 推論ごとの予測action chunk全体と、そのうち実際に環境で実行した部分（実行したステップ数）を区別して記録
- 区間ID: 推論呼び出しの単位、またはskill IDの切り替わりの単位。どちらを使ったかを記録
- 手先の位置・姿勢・グリッパー（`robot0_eef_pos` 等）。G2で運動の類似度に使う

一度の記録でG0・G1・G2の全部に使えるようにし、ゲートごとに取り直さない。
G2用の action expert の隠れ状態も、記録時に保存できるようにする（オプションで有効化）。

保存形式（G2解析と共通。変更する場合は両方を合わせる）:
- `<run_dir>/manifest.json`: 実行条件、チェックポイント、suite・タスク・初期状態ID・エピソードの一覧、区間IDの定義、隠れ状態の層・時刻・集約方法。
- `<run_dir>/episodes/<episode_id>.npz`: 推論呼び出しごとに1行（長さN）の配列として以下を保存する。
  `step`（N）、`proprio`（N×Ds）、`eef_pos`・`eef_quat`・`gripper`（各ステップの環境の値。エピソードの全ステップ分を別キー `env_*` で保存）、
  `pred_chunk`（N×H×Da）、`n_executed`（N）、`skills`・`skill_mask`（N×L）、`segment_id`（N）、
  任意で `feat__<名前>`（N×D）。名前の例: `L17_mean_t_last`（層・集約方法・拡散時刻）。
  画像は G0・G1 のオフライン再入力に必要な分だけ、別キー（`img_*`、uint8・縮小可）で保存する。
- エピソードのメタ情報（task, suite, init_state_id, success）は manifest に書く。
G0・G1は、保存した観測をサーバーなしでオフラインに再入力して使えるようにする。
（ポリシーを直接ロードし、`skills` を差し替えて `sample_actions` を呼ぶ。乱数シード・ノイズを固定する）

## G0: skill経路の感度

保存した観測（libero_spatial / object / goal / 10 の各数タスク×少数初期状態、合計数百ステップ程度）に対して、
同じ観測・同じ拡散ノイズで、skillsだけを次の条件に変えて推論する。

1. 正解（記録した値）
2. 同じsuite内の別のskill IDにシャッフル
3. 全トークンをmaskする。不可能ならゼロ埋め込みにする（どの方法で行ったかを明記）
4. 参考: ノイズのシードだけを変えた場合（方策そのもののばらつき）

指標: 正解条件との action chunk のL2距離（ステップ別・次元別。位置・回転・グリッパーに分ける）を、ノイズによるばらつき（条件4）と比べる。
可能なら各層のエキスパート選択の変化率も出す。
少数のオンライン実行（例: spatial 数タスク×数試行で、正解とシャッフル）で成功率の変化も見る。

判定:
- skillを変えた差がノイズのばらつきより明確に大きく、成功率も落ちる → skill経路は行動を左右している。メモリ注入点の候補として残す。
- 差がノイズと同程度 → skill embedding への注入は行わない。suffixトークンや adaRMS 条件への注入を次の候補にする。

## G1: 合成の妥当性（重み付き和）

同じ観測で、2つのskill埋め込み e_a, e_b を α∈{0, 0.25, 0.5, 0.75, 1} で線形補間し、skill_embeds として入力する。
（`skill_embed` の後段で差し替えるフックが必要）

比較として、補間せずに2トークンを並べ、mask付きのattentionに任せる条件も入れる（既存のcross-attentionが集合を受け付けるため）。

指標: 出力する行動が α に対してなめらかに変わるか。中間値で、どちらの端点からも離れた「平均化した行動」になるか。

判定:
- なめらかで、端点の間に収まる → ベクトルの重み付き和を使う。
- 破綻する → 和ではなく、複数トークン（集合）として条件付ける。

## G2: 内部特徴は運動を表しているか（G0・G1の後）

action expert の層ごとの隠れ状態（suffix側。拡散の最終ステップなど、使った時刻を明記）を、推論ごとに集約して保存する。
検索の質問側（クエリ）と保存側をエピソード・初期状態単位で分け、同一エピソードの隣接窓は除く。
kNNで取ってきた区間の手先の動き（その後Hステップの相対変位・回転・グリッパー）が、クエリのものとどれだけ近いかを測る。
比較対象: ロボット状態だけのkNN、ランダム検索、層・集約方法の違い。

判定: 内部特徴がロボット状態だけのkNNを明確に上回らなければ、暫定の保存表現として使う価値は低い。その場合は運動エンコーダの学習へ早めに移る。
