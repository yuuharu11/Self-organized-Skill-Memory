# 発表の筋書き：スキルメモリで未学習タスクに汎化する

スライドの流れの案と、各段の根拠（実験・数値・注意点）の対応表。

## 決めた流れ（原文）

スキルを構築したい
→ 圧縮表現を考える
→ 圧縮誤差を見る（DCT, PCA, Codec, VQ-VAE）など
→ gripperは別表現で見たほうがいい（予備実験）
→ 可変長を保存するほうが本質的（予備実験）
→ gripperとそれ以外で変化をもとに区間分割して時間方向でDCTに圧縮
→ 未解決？：gripperはどうするのか / 大きさはどう決めるか
→ キーを考える
→ デフォルトの方法だとうまく取れない（VLM平均、アクション履歴の射影層）
→ クロスアテンションを考える
→ JEPAを検討する
→ 学習方法を検討する（対照学習）
→ latent tokenに基づいて直積で類似をかける
→ MSEに応じてノイズの強さを変える
→ Expertの学習も行う
→ 最終結果

以下の表は、この流れに今ある結果を当てはめたもの。
数値の出どころの `.skillnet-state/` はローカルの実行記録（Git 管理外）。09 の §7 以降と 10 の後半は、まだ main ではなく作業ツリー（`worktrees/query-invariance`、`worktrees/robocasa-latent`）の experiments.md にある。

状態の凡例：**結果あり**（スライドに使える）／**否定的結果**（効かなかったことが言える）／**未完**（実行途中・未集約）／**未実施**／**要取り直し**（† 逆さ画像の数値）

## 診断

1. **前半（#1〜#5）は根拠が揃っている。** ただし #2 は「DCT・PCA・Codec・VQ を同じ条件で比べた」とは言えない。言うなら、09 §2 と同じ条件で VQ（と Codec）を1回足す必要がある。
2. **後半（#7〜#13）は、どの段も閉ループで 43 を超えていない。** 「積み上げて最終結果」という筋は今のままでは成り立たない。成り立たせるには、次のどちらかが要る。
   - (a) 最終構成（区間分割キー R5 ＋ Expert ＋ 適応ノイズ）を1本通し、43 を超える閉ループの結果を出す。
   - (b) 後半を「何が律速か」の診断として話す。主張は「型は十分（正解で選べば .079）、律速は選び方と向き」。ただしこれはオフライン MSE からの主張で、オフライン MSE は閉ループを予測しなかった（MAG3 は Dev を通って 5/100、R5 は Eval で P5 に勝って 33/100）。RoboCasa でも「選択が主因」は撤回し、先頭5ステップの MSE は動きの持続を評価してしまうと分かっている。(b) にするなら、この物差しの問題自体を1枚にする。
3. **#7 の言い方は直した。**「履歴の射影層ではうまく取れない」は 09 の数値と合わないので、「履歴は真のときは最良だが、壊れると戻れない、場面の情報を持たない」とした。この方が #8〜#11（画像を読む、場面不変、壊れに強いキー）への動機にもなる。
4. **順序が実際と違う箇所。** ノイズの適応（#12）は 07 で先にやっている。大きさ（#6 の MAG）はキーの後にやった。スライドの順序は論理の順でよいが、#12 は「既知タスクでの結果」と明記する。
5. **指標の混在に注意。** MSE6 には単純平均と ×6/7 の2つの定義がある。直前保持は .114（09 §5）と .133（INV1 で同じ行を再計算）で値が違う。† の数値は逆さの画像で計算している。1枚のスライドに異なる定義の数値を並べない。
6. **ノートの置き場所。** main の 09 は §6 で止まっていて、§7〜12 と LIB1 は作業ツリー `query-invariance`（PR #17、draft）にある。RoboCasa の 10 も、後半は作業ツリー `robocasa-latent` にある。研究ノート README の「現在地」も古い。スライドを作る前に main へ集約するのが望ましい。
