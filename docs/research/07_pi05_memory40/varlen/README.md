# 可変長の運動区間メモリ：選んで追従する診断

問いは、10-step 下書きを毎回検索する代わりに、区間開始時に一度メモリ区間を選び、その後を経過時間または位相で追従すると改善するか。Expert は再学習せず、既存 `run-01/bridge/001500` を使用した。

## 結論

**キーで選んだ区間を一度だけ使う方式は、固定10-stepを毎回選び直す方式を上回らなかった。** t0=.2 の全548行では S-grip の下書き追従が固定検索より +.0228〜+.0283 MSE 悪く、episode bootstrap 95% CI はそれぞれ正の値だけを含んだ。S-grip+vel は +.0251〜+.0264 で同じく悪化。t0=.4 では差が小さく、CI は0を含む。評価区間全体を見て最良メモリ区間を選ぶ oracle は t0=.2 で固定検索より .0135〜.0138 MSE 良かったが、これは実行時に使えない上限である。区間は有望な候補を含むが、開始時キーによる選択と追従がボトルネックだった。

この診断では Long Eval の正解行動から区間境界を作った。これは依頼どおりの境界を使ったオフライン比較であり、実行時の境界検出性能は評価していない。

## 区切りと検索

- run-01 の source parquet を読み、10Hz の元フレームから分割した。アクションは run-01 の正規化済み `[10,32]` 窓をstride10で連結して保存した。
- S-grip は元アクションのグリッパー指令（index 6）の符号切替で区切り、最短長を10フレーム（1秒）にした。
- S-grip+vel は同じ境界に、state の先頭3成分（LIBERO EEF xyz）の差分から求めた速度ノルムを5フレーム平滑化し、その局所極小を加えた。速度しきい値は Long 外Devだけで選択。候補分位点のうち q=.50、0.0845 m/s が選ばれ、Dev 区間の中央値は2.4秒、75.4%が1〜4秒だった。
- メモリには task 10〜39 の run-01 memory episode のみを使用。Long task 0〜9 と Long Eval episode の非混入を assert した。Long Eval の548 query（hard 63）は評価時だけ境界を作る。
- 区間開始キーは保存済み retrieval-4b の frozen `wrist_state_contrastive` 64次元埋め込みと cosine。区間開始でTop-1を選び、そのepisodeの残りは再検索しない。候補は Long 外 memory のみ。時間合わせは経過フレーム維持と区間長比の位相合わせ。
- 固定10-step対照は同じ frozen 64DキーでLong外 memory rowsを再順位付けし、各 query row でTop-1を引き直す。既存 all40 候補一覧は他のLong taskも含み得るため、そのまま使わずLong外候補だけで再計算した。

## 区間統計

単位の長さは実フレームを10Hzで秒に換算。異なるタスクにある10-frame先頭行動の最近傍MSEも、行動特徴の共有度の参考値として示す（閾値 .01 は記述用で、学習・選択には使わない）。

| メモリ分割 | 区間数 | 長さ中央値 [p10,p90] 秒 | 最近傍の別タスク区間：先頭10-frame MSE中央値 | 最近傍MSE≤.01の割合 |
|---|---:|---:|---:|---:|
| 固定10-step | 3,857 | 1.0 [1.0,1.0] | .0185 | 22.7% |
| S-grip | 744 | 4.8 [1.4,8.67] | .0145 | 33.2% |
| S-grip+vel | 1,260 | 2.5 [1.2,6.0] | .0206 | 20.3% |

Long Eval側は S-grip 85区間（中央値6.2秒、p10/p90=1.98/10.62秒）、S-grip+vel 203区間（中央値2.2秒、p10/p90=1.1/5.1秒）に分かれた。

### 対照の再利用と版の違い

- 通常π0.5単発の既存予測・row errorは、今回の query order と truth に一致することを確認した。ゼロ下書きは同じseedで再生成。既存 topk-long seed 4101のrow MSEとの平均絶対差は t0=.2で1.58e−5（最大 .000239）、t0=.4で1.21e−5（最大 .000352）で、完全一致ではないため既存ゼロ結果の代用ではなく今回の再生成値を表に載せた。
- 初期集計ではoracle選択IDを区間順に連結し、query row順と誤って対応させたため、oracle下書きが実検索より悪く見えた。各区間のoracle IDを対応するquery row indexへ直接格納するよう修正した。final-02以降で、oracleは固定検索より良い。
- 初期の固定検索候補一覧には別のLong taskのmemory rowが混在し得たので、同一の64D retrieval-4b keyでtask 10〜39 memoryだけを再順位付けした。
- 版の違い：出力直下の初回準備結果はoracle IDの行対応がずれた中間集計。`final-01` は行対応修正後の準備途中でJSON保存エラーにより停止し、生成後評価なし。`final-02` は修正済み行対応で完走したが、速度を指令Δxyzから近似していた。`final-03` は同じ準備配列がfinal-02と完全一致することをassertし、Long Eval区間統計を追加して、final-02の生成後予測を再利用した。**`final-04` はLIBERO stateの実EEF xyz差分を使うよう速度計算を直し、Devしきい値・区間・下書きと生成後評価をすべて作り直した最終版**である。
