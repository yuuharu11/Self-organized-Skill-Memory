# 査読：S2 閉ループ評価と、LIBERO-Skill で SkillNet を上回るまでの最短経路

作成：2026-10-29。対象は S2（π0.5 / SkillNet LIBERO-90 の action expert に、スキルメモリのアンカーを開始点として入れる版）と、軽量版 v2.1 / review-v2。
立場：VLA（π0/π0.5、flow matching の行動ヘッド）と LIBERO 評価を専門とする査読者。コードと既存文書は編集していない。数値は、下記のファイルを 2026-10-29 13:40 UTC 頃に読んだ時点のもの（評価は進行中）。

## 0. 結論（先に）

1. **S2 の行動ヘッドの学習目標に、構想と軽量版から外れた誤りがある。** アンカー行の速度目標が `ε − A` になっている。この目標で学習すると、アンカーのずれを最後まで直さず、`(1 − t0)·(a − A)` が残る方向に学習する。軽量版はこの問題のない目標（`x_t − t·F = A`）を使っていた。S1 の好結果は、S2 の実装には引き継がれていない（§4-1）。
2. **取り出しは、実質的に一様ランダムになっている。** 閉ループのクエリでは、最大コサイン類似度の平均が 0.997（最小 0.988）、正規化エントロピーの平均が 0.97。57 単位からほぼ無作為に 1 つを引き、提案条件のクエリの約半分で t0=0.6 から始めている。残りの半分は t0=1.0、つまりスキルを使わない純粋なノイズから始まる。これは「行動は常にスキルから」という構想にも合っていない（§1）。
3. LIBERO-90 の既知タスクで成功率が下がったのは偶然ではない。対応のある 200 試行のうち、提案だけが失敗したのが 20 件、提案だけが成功したのが 2 件（符号検定 p≈1.2×10⁻⁴）。原因は「質の低いアンカー × ずれが残る目標 × 0.25 秒ごとに独立して選び直すこと」の組み合わせと考えるのが最も整合的。ただし、3 つを切り分けるデータはまだない（§1）。
4. **SkillNet 44.5% との比較の前提が成り立っていない。** 微調整後・アンカーなしの Skill 02〜09 は、途中集計でおよそ 31%（論文の π0.5 28.5% に近い）。公開 SkillNet を同じハーネスで測ったのは 1/160 試行だけ。ハーネスが 44.5% を再現するのか、微調整で汎化が壊れたのかが分からないまま、提案と比べている（§4）。
5. 最短経路：(0) 公開 SkillNet を同じハーネスで測る → (1) 目標の修正をオフラインで検証する → (2) クエリ鍵を作り直し、スキルを持続させる → (3) 既知タスクで劣化しないことを確かめる → (4) Skill 02〜09 の 20 試行で予備評価 → 50 試行で本番。H200 1 枚で約 4〜5 日（§3）。

ここから言えること：

- **劣化はアンカーを使った経路に由来する。** t0=1 のクエリは、アンカーなしとビット単位で同じ経路を通る（`pi0_anchor_flow.py` の `lax.cond`、smoke で確認済み）。差を生むのは t0=0.6 のクエリだけ。
- **アンカーの質は、ほぼランダム並み。** 類似度が 0.997 に集まっているため、温度 0.001 をかけても重みは広く散る。選ばれる単位の中身は、中央値で約 70 タスクにまたがる 0.5 秒のかけら。既知タスクでも、正しい運動の型を引けていない。
- **オフラインの MSE 改善（−5%）は、閉ループの −9 ポイントを予測していない**（§2）。

### 1.2 実装から言えること（データではなくコードからの推論）

**(a) 目標の不整合：アンカーのずれを最後まで直さない。** `pi0_anchor_flow.py: compute_anchor_loss` は次の形になっている。

```
x_t = (1 − t)·a + t·ε,   目標 v* = ε − A      （a：取り出したアンカー、A：正解）
```

推論は `x_{t0} = (1 − t0)·a + t0·ε` から始め、`x ← x − Δt·v` で 0 まで Euler 積分する。学習した通りにヘッドが常に `ε − A` を出すとすると、到達点は次のようになる。

```
x_0 = x_{t0} − t0·(ε − A) = (1 − t0)·a + t0·A
```

つまり、アンカーのずれ `(a − A)` の **(1 − t0) 倍（t0=0.6 なら 40%）が最終行動に残る**。正解に最後まで到達させるには、目標を整合した速度 `(x_t − A)/t = ε − A + (1 − t)(a − A)/t` にする必要がある。これは軽量版の `anchored = ||x_t − t·F − A||²` と同じ。あるいは v2 文書のブリッジ型の経路 `x_t = (1 − t)A + t·x_src`、目標 `x_src − A` でもよい。

一方、通常の経路だけで学習したヘッド（公開 SkillNet）を、SDEdit のように途中のノイズ量から使う場合は、ε を推定し直すのでこの偏りは原理的には生じない（Meng et al. 2021）。**S2 の微調整は、アンカー行の 60%＋1/15 で「直さない」ことを積極的に教えている。** これが、既知タスクで正しい行動を出せていた方策を劣化させた、最も有力な仕組み。

- 正規化した行動空間で、無関係な単位とのずれの 40% が残れば、グリッパーの符号や把持前の位置合わせが崩れる。既知タスクのうち、把持や引き出しの取っ手の位置合わせが要るもの（task 3、4、7、8）で下がっていることと矛盾しない。
- **未検証**：これは理想化した解析。実際のネットは x_t から a と ε を分けられないので、残り方は 0 から (1 − t0) の間になる。§3 の段階 1 で、**残差の比率**（`x_0 − A` を `a − A` に回帰したときの係数）を測れば数分で確定できる。

**(b) 毎回選び直すこと（replan=5）と、0.5 秒の単位。** 行動チャンクは 10 ステップ（0.5 秒）で、そのうち 5 ステップを実行して再計画する。提案は 0.25 秒ごとに、ほぼ一様な重みから単位を**独立に**サンプルし直す。前のチャンクとの連続性はない。続く単位が中央値 0.5 秒で切り替わること（単位の解釈）と合わせると、アンカーが 0.25 秒ごとに無関係な方向へ跳ぶ。両方成功した試行が数％長いことはこれと矛盾しないが、ジャークやグリッパーの反転の記録がないので、確定はできない。

**(c) 鍵が状態と進み具合を表していない。** `discrete_state_input=False` なので、鍵は「画像＋指示文」の全プレフィックスの平均プーリングで、状態のトークンは入っていない（checker-review に明記）。さらに instruction_only なので、文のトークンはエピソードの間ずっと同じ。平均プーリングの表現は、共通成分（文・背景）に支配されて異方的になる。類似度が 0.997 に集まることはこれと整合する。結果として、**鍵は「どのタスクか」程度しか区別できず、エピソードの中の段階（近づく／掴む／運ぶ）を区別できない**。

### 1.3 データからは言えないこと

- (a) 目標、(b) 選び直し、(c) 鍵の質のうち、どれが主因かは分けられない。同じ微調整ヘッドで「正解の単位を強制した場合」や「目標を直したヘッド」の閉ループがないため。
- **微調整そのものの影響。** LIBERO-90 で「公開 SkillNet・アンカーなし」を測っていないので、95.5% が公開の重みより下がっているかは分からない。ただし LIBERO-10 task 0 では、公開の重み＋アンカーが 6/20、微調整＋アンカーが 2/20、微調整・アンカーなしも 2/20（対応差 +0.20、95% 区間 [0.05, 0.40]）。微調整が汎化を損ねた疑いがある（1 タスクだけ）。
- t0 と反復回数の効果は分けられない。n = round(10·t0) と、刻み幅を一定にしているため（R6 の格子は閉ループで未実施）。
- LIBERO-10 のゼロショットでほぼ全滅しているのは、全条件に共通（アンカーなしも 0〜10%）。アンカーの効果ではなく、90 で学習した重みの限界。この suite からアンカーの良し悪しは言えない。
- 失敗の種類（把持ミス、グリッパーの早開き、時間切れ）は記録されていない。チャンクごとの行動も保存されていないので、事後にグリッパーの反転を数えることもできない。

### 1.4 LIBERO-Skill の途中経過の読み方

対応のある試行のうち、提案だけ成功が 17、アンカーなしだけ成功が 11（符号検定 p≈0.34、有意でない）。skill_obj_02（6 対 1）と skill_obj_06（5 対 1）は提案が良く見えるが、Skill にはシャッフル対照がない（1 試行だけ）。そのため「単位の中身が効いた」のか、「ランダムな摂動で行き詰まりを抜けた」のかを区別できない。既知タスクでは摂動が害になり、未知タスクで行き詰まっている方策には時に益になる、という読み方とも整合する。**現状のデータは、構想（スキルが汎化を生む）の証拠にも反証にもならない。**

## 2. 軽量版のオフライン指標（行動の MSE）は、閉ループを予測できているか

**予測できていない。** 証拠は次のとおり。

- S2 の較正：保留した LIBERO-90 で MSE が 5% 改善したのに、同じ分布の閉ループでは −9 ポイント。
- 軽量版の公平比較：改善の 2/3〜3/4 がグリッパーの次元で、手先の位置はほとんど改善していない。改善の多くは「通常の F のグリッパー出力が 0 付近で揺れる」ことの修正であり、π0.5 では起きない現象。
- review-v2：既知条件（D1）でも、F_normal より悪化するクエリが 5〜7% ある。1 エピソードのクエリは 15〜80 回あるので、クエリ単位で 5% の悪化が独立に起きれば、1 回以上起きる確率はほぼ 1 になる。致命的かどうかは悪化の種類（グリッパー、位置合わせ）次第で、平均 MSE には表れない。
- 1 本のデモとの MSE は、平均的な行動を有利にする。アンカーに平均を取った中心を使うと MSE は下がるが、閉ループでは中途半端な行動になる（往復テストで、終端の位置が 18→45 mm ずれる）。

### 軽量版で測るべきもの（すべて、対応のあるクエリでの F_normal との差、3 seed）

| 指標 | 何を予測するか | 合格の目安 |
| --- | --- | --- |
| **残差の比率**：誤ったスキルを強制したときの `‖x_0 − A‖ / ‖a − A‖` を t0 ごとに | ヘッドがずれを最後まで直すか（§1.2(a)） | t0 ≥ 0.6 で ≤ 0.2。現行の目標なら ≈ (1 − t0) になるはず |
| **大きく悪化するクエリの率**：位置の終端誤差が F_normal より 1 cm 以上悪化、またはグリッパーの符号が正解と逆になったクエリの率（確信度ビン別） | エピソードの失敗につながる悪化 | 全ビンで ≤ 1%。1 エピソードあたりの期待件数 < 0.3 |
| **実行する 5 ステップ**の手先終端誤差（mm）とグリッパーの切り替えタイミングの誤差 | 実際に実行される部分の精度。10 ステップ全体の MSE ではなく | F_normal 以下 |
| **チャンクの境目の不連続**：前のチャンクの 6〜10 ステップ目と、次のチャンクの 1〜5 ステップ目の差 | 選び直しによる跳び（§1.2(b)） | F_normal の 1.2 倍以内 |

指標の妥当性も確かめる：すでに閉ループがある S2 の条件（微調整・アンカーなし、提案、公開＋アンカー）で上の指標を計算し、閉ループの順位と一致するかを見る。一致しない指標は使わない。

## 3. 構想を守ったまま、LIBERO-Skill で 44.5% を上回る最短の実験計画

前提（構想の制約）：行動は毎回スキルから始める。スキルはラベルなしで形成し、勾配なしで追加できる。条件は画像・サブタスク・状態の埋め込みだけ。ノイズ量と反復回数は信頼度で決める。LIBERO-10 と Skill のデータは、学習・メモリ・選択に一切使わない。

**t0 の上限について**：現行の較正は、信頼度ビンの半分で t0=1.0（スキルを使わない）を選んでいる。これは「行動は常にスキルから」と合わない。低い信頼度でも t0 ≤ 0.9 に制限し、誤ったスキルからでも戻れることは、学習（v2 文書の (a)〜(e) の混合、ただし整合した目標）で保証する。これが構想どおりの形。

時間の見積もりの根拠：微調整は実測 1.0〜1.1 秒/ステップ（20k ステップで 6.1 時間）。閉ループは、H200 1 枚・サーバー 1 つ・8 環境で 21〜31 試行/時（`anchor-s2-zero-shot-…/report.md`）。Skill は失敗すると 1600 ステップまで走るので、**15〜22 試行/時**と見込む。いずれも見積もりで、最初のケースで実測して修正する。

| --- | --- | --- | --- |

| **4. Skill の予備評価** | Skill 02〜09 × 20 × {公開・アンカーなし（段 0 を再利用）、提案、シャッフルしたメモリ} | 提案 > アンカーなし（対応差の 95% 区間の下限 > 0）、提案 > シャッフル、点推定 ≥ 45% | 320 試行 ≈ 15〜21 時間 |
| **5. 本番** | 8 × 50（論文と同じ試行数）× {公開・アンカーなし、提案}。シャッフルは 20 試行の結果を保持。追加で、skill_obj_03（LIBERO-10 task 3 とほぼ重複）を除いた集計 | 提案の 8 タスク平均 > 44.5%、Wilson 区間の下限 > 公開 SkillNet の実測値。タスク別の表を付ける | 800 試行 ≈ 36〜53 時間 |

**合計：段 0〜4 で約 2〜2.5 日、段 5 まで含めて約 4〜5 日。** 段 2′ が必要なら +3 時間。段 0 と段 1〜2 は CPU/GPU を分けて並行できる（閉ループは 1 サーバー、オフライン解析は同じ GPU の空き時間で）。

勝てる見込みについて：公開 SkillNet がハーネスで約 44% を出し、提案がそれに +数ポイントを乗せる、というのが必要条件。すでに SkillNet より低い微調整ヘッド（約 31%）からは、アンカーで +14 ポイントを出す必要があり、非現実的。**段 0 の結果で、どちらの重みから出発するかを決めることが最大の分岐**になる。

## 4. S2 の実装と評価手順の誤り・不公平

| # | 種類 | 指摘 | 影響と対応 |
| --- | --- | --- | --- |
| 1 | **誤り（重大）** | `compute_anchor_loss` の目標が `ε − A`。アンカー経路と整合する目標は `(x_t − A)/t`。軽量版（`x_t − t·F − A`）とも異なる。DESIGN.md の式そのものが不整合で、checker は「DESIGN の明示式どおり」として通している。docstring の「imperfect anchor を直すよう学習する」は成り立たない | 既知タスクの劣化の最有力原因。段 1 で確定させ、修正する |
| 2 | **基準の欠落（重大）** | 44.5% と比べている一方、同じハーネスでの公開 SkillNet は 1/160 試行。比較している 2 条件は、どちらも微調整後の重み | 段 0 を必須にする。微調整・アンカーなし（約 31%）は SkillNet の代わりにならない |
| 3 | 構想との不一致 | 較正が半数のクエリで t0=1.0（スキルなし）を選ぶ。t0 の候補に 1.0 が含まれる | 「常にスキルから」を満たさない。上限 ≤ 0.9。提案の効果が半分に薄まる点にも注意 |
| 4 | 設計との不一致 | 鍵に状態が入っていない（`discrete_state_input=False`）。DESIGN は「画像・文・状態のプレフィックス」と書いている | 段階を区別できない。状態を明示的に連結する |
| 5 | 学習と推論の不一致 | 学習のアンカーは、同じタスクの全収録を除いたメモリから取る。推論の既知タスクでは同じタスクの単位も候補に入る。学習の t は Beta(1.5,1) で全範囲だが、推論の開始は t0 ∈ {0.6} だけ | 既知タスクの評価条件が、学習で見た分布の外。修正後は、推論で使う t0 の範囲を重点的に学習する |
| 6 | 微調整の設定 | 55,660 行（約 14 行/エピソード）に 20k × 32 ＝ 約 11.5 エポック。画像の拡張なし（`train=False` の既定）。通常の経路は 1/3 だけ。保留データでの通常の経路の誤差を記録していない | 公開ヘッドからずれ、汎化が損なわれた可能性（LIBERO-10 task 0：公開＋アンカー 6/20、微調整 2/20）。段 2′ の設定に反映する |
| 7 | 対照の欠落 | Skill にシャッフル対照がない（1 試行）。LIBERO-90 に公開・アンカーなしがない | Skill での差を単位の中身に帰属できない。段 4 で 3 条件にする |
| 8 | 試行数と初期状態 | 20 試行/タスク（論文 50 の先頭 20）。Skill の環境 seed は 7 に固定、非 Skill は 7+index。8 タスク × 20 の Wilson 区間は約 ±7 ポイント | 44.5% との比較は 50 試行で。報告では明記済みなので、本番で揃える |
| 9 | ラベルの扱い | 全条件で SkillNet のルーターにタスク単位のスキル注釈（人手の組み合わせラベル）を入れている。SkillNet の公開手順と同じなので比較は公平。ただし「ラベルなし」の主張とぶつかる | 主張は「メモリと開始分布はラベルなし。プリミティブの MoE は SkillNet の注釈付きルーターを継承」と限定して書く。可能なら注釈を一定値にした場合の感度も示す |
| 10 | 細部（いまは影響なし） | `sample_actions_from_anchor` は位置埋め込みの長さに `skills.shape[1]` を使う（上流は `objects.shape[1]`）。`_apply_skill_embed_override` を通さない。学習側は位置埋め込みを連結しない。この設定は `positional_encoding=False` なので結果には影響しない。また smoke は t0=1 の委譲経路しか一致を確かめておらず、アンカー経路で t0→1 としたときに上流と一致するかは未検証 | 将来の設定変更で黙って壊れる。`sample_actions_from_anchor(t0=1)` と上流の一致テストを加える |
| 11 | 診断の不足 | チャンクごとの行動、グリッパーのイベント、失敗の種類を記録していない | §2 の指標を閉ループでも計算できるよう、行動チャンクを保存する（軽い） |

評価手順のうち、良くできている点：同じ初期状態・seed・問い合わせ乱数を対応させていること。t0=1 がビット単位で同じ経路を通ること。エラーを分母に含めること。LIBERO-10 と Skill を較正にまったく使っていないこと。skill_obj_03 の重複を明示していること。これらは本番でも維持する。
